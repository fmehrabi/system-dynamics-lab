# افزودن مدل جدید به System Dynamics Lab

این پروژه از الگوی **Model Package + Central Registry** استفاده می‌کند. هر مدل یک بسته مستقل است و صفحه کتابخانه فقط Registry را می‌خواند.

## ساختار الزامی هر بسته مدل

برای مثال، مدل جدیدی با شناسه `marketing-dynamics`:

```text
models/
└── marketing-dynamics/
    ├── manifest.json
    ├── source.mdl
    ├── engine.js
    ├── app.js
    ├── index.html
    ├── tests/
    │   └── test_engine.js
    └── preview.png
```

### نقش فایل‌ها

| فایل | مسئولیت |
|---|---|
| `manifest.json` | شناسه، عنوان، توضیح، نسخه، دسته، زمان شبیه‌سازی، فایل منبع و وضعیت اعتبارسنجی |
| `source.mdl` | نسخه اصلی و دست‌نخورده فایل Vensim ارسالی |
| `engine.js` | معادلات، Lookupها، روش انتگرال‌گیری، شرایط اولیه، اعتبارسنجی ورودی و خروجی سری زمانی |
| `app.js` | نگاشت متغیرها به دیاگرام، کنترل‌های مجاز، نمودارها و رفتارهای اختصاصی صفحه مدل |
| `index.html` | صفحه مدل؛ از تم مشترک `../../shared/style.css` استفاده می‌کند |
| `tests/` | تست معادلات، شرایط اولیه، گام اول، Lookup و سناریوهای حساسیت |
| `preview.png` | تصویر کارت مدل در کتابخانه |

## افزودن به Registry

فایل `models/registry.json` را باز کن و یک شیء جدید به آرایه `models` اضافه کن. نمونه:

```json
{
  "id": "marketing-dynamics",
  "title": "Marketing Dynamics",
  "description": "An interactive model of marketing response and sales dynamics.",
  "category": "Marketing Systems",
  "status": "available",
  "version": "1.0.0",
  "path": "./models/marketing-dynamics/",
  "manifest": "./models/marketing-dynamics/manifest.json",
  "thumbnail": "./models/marketing-dynamics/preview.png",
  "tags": ["Marketing", "Feedback", "Vensim"],
  "order": 2
}
```

پس از Commit شدن Registry، صفحه اصلی کارت مدل را خودکار نمایش می‌دهد. نیازی به ویرایش `index.html` یا `assets/library.js` نیست.

## قرارداد موتور شبیه‌سازی

هر `engine.js` باید یک API مستقل با نام `window.SDExplorerEngine` ارائه دهد. رابط فعلی از این اعضا استفاده می‌کند:

- `DEFAULTS`: مقادیر پایه پارامترها و شرایط اولیه
- `DT` و `FINAL`: گام زمانی و زمان پایان
- `LOOKUP` و `LIMITS`: در صورت وجود Lookup و حدود مجاز رابط کاربری
- `clone(value)`: کپی مستقل تنظیمات سناریو
- `simulate(parameters)`: اجرای مدل و بازگرداندن `rows`, `params`, `warnings`
- `at(run, time)`: دریافت ردیف خروجی نزدیک به زمان انتخاب‌شده

برای مدل‌های بدون Lookup، `LOOKUP` و `LIMITS` می‌توانند متناسب با رابط همان مدل تعریف شوند؛ نباید برای سازگار کردن ظاهری، پارامتر یا معادله ساختگی اضافه شود. در صورت تفاوت ماهوی مدل، `app.js` همان بسته باید رابط مناسب آن مدل را پیاده‌سازی کند.

هر ردیف `rows` باید حداقل زمان را در کلید `t` و مقادیر متغیرها را در کلیدهایی با نام‌های پایدار و مستند داشته باشد. از تغییر نام کلیدها پس از انتشار نسخه مدل خودداری کن؛ اگر لازم شد، نسخه مدل را افزایش بده.

## ترتیب بررسی و انتشار

1. فایل MDL را بخوان و فهرست Stock، Flow، Auxiliary، Constant، Lookup و تنظیمات Control را استخراج کن.
2. برای هر متغیر، معادله، واحد، علل (Causes) و متغیرهای متأثر (Uses) را ثبت کن.
3. دیاگرام را از روی ارتباطات واقعی مدل بساز؛ مسیر Flow را با رابطه علّی اشتباه نگیر.
4. مشخص کن کدام پارامترها و شرایط اولیه اجازه ویرایش دارند. متغیرهای محاسبه‌شده را فقط خواندنی نگه دار.
5. موتور عددی را پیاده‌سازی و تست کن: مقادیر اولیه، اولین گام، Lookup، حدود، و چند سناریوی تغییر پارامتر.
6. در صورت امکان، خروجی Vensim را به CSV صادر و با خروجی مرورگر به‌صورت زمان‌به‌زمان مقایسه کن. خطای مطلق و نسبی را گزارش کن.
7. صفحه را در عرض دسکتاپ و موبایل آزمایش کن؛ سپس پیش‌نمایش و Registry را به‌روزرسانی کن.
8. فقط پس از گذراندن بررسی‌ها، `status` را از `draft` به `available` تغییر بده.

## قواعد نگهداری

- فایل اصلی MDL را بدون بازنویسی یا اصلاح، در بسته مدل نگه دار.
- هرگز معادلات دو مدل را در یک engine مشترک مخلوط نکن.
- از شناسه‌های کوتاه، lowercase و kebab-case استفاده کن؛ شناسه منتشرشده را تغییر نده.
- پارامترهای UI را از مقادیر واقعی معادلات جدا نگه دار و هر محدودیت رابط را مستند کن.
- مدل ناقص یا تأییدنشده را با `status: "draft"` ثبت کن؛ مدل draft نباید به‌عنوان مدل آماده معرفی شود.
- تم عمومی را فقط در `shared/style.css` تغییر بده؛ تغییر یک مدل نباید ظاهر مدل‌های دیگر را ناخواسته بشکند.
